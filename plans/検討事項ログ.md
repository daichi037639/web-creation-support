## LOG-001: 生成サイトのコード形式（静的HTML vs Next.js）

**起票日**: 2026-06-28
**状態**: 方針決定 / 詳細は要検討

### 選択肢

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| 静的HTML/CSS/JS | シンプル・管理容易・ホスティング無料 | 動的機能が作れない（問い合わせフォームなど） |
| Next.js | 動的機能が作れる・拡張性高い | 初心者の管理負担増・デプロイがやや複雑 |

### 決定した方針

機能の複雑さでシステムが自動判定・提案する：

- **静的HTML**: 会社紹介・商品紹介・ギャラリーなどシンプルなサイト
- **Next.js**: 問い合わせフォーム・予約・DB連携など動的機能が必要な場合

ウィザードの STEP 4（サイト構成）で希望機能を入力した時点で判定し、ユーザーに提示する。

### 残課題

- 自動判定の閾値・ロジックの詳細設計
- 「静的で始めてあとでNext.jsに移行」というパスを許容するか

## LOG-002: デプロイ方式（ユーザーアカウント vs サービス代理）

**起票日**: 2026-06-28
**状態**: 方針決定 / 再検討の余地あり

### 選択肢

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| A: ユーザー自身のアカウント | このサービスを使わなくても自分で管理できる・自立性が高い | GitHub/Vercelのアカウント作成手順をユーザーがこなす必要あり |
| B: サービス側で代理デプロイ | ユーザー体験がシンプル・サービスへの粘着性が上がる | サービスがなくなると管理不能になる・ベンダーロックイン |

### 決定した方針

**A: ユーザー自身のアカウント**を優先する。

理由：このサービスがなくなっても事業者が自分のサイトを管理できる自立性を重視する。
そのため、サービス内でGitHub・Vercelのアカウント作成〜デプロイまでの手順をわかりやすくガイドする。

### 再検討のトリガー

- ユーザーテストで「アカウント作成が障壁になっている」という結果が出た場合
- サービスの粘着性（継続率）が目標を大きく下回った場合

→ その際はB（代理デプロイ）に切り替えるか、A+Bのハイブリッドを検討する。

## LOG-005: 業界別の質問出し分け方式（静的質問バンク vs AI動的生成）

**起票日**: 2026-07-12
**状態**: MVP方針決定

### 背景

「飲食店に『顧客の悩みや不満』と聞くのは不自然」など、業界によって適切な質問が異なる。

### 選択肢

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| A: 静的質問バンク + 業界別言い換え | 品質を人間が管理できる・実装が単純・APIコスト0 | 業界追加のたびに手作業・カバレッジに限界 |
| B: AIが業界に応じて質問を動的生成 | どんな業界にも対応・柔軟 | 質問品質が不安定・毎回APIコスト・テスト困難 |

### 決定した方針

**A: 静的質問バンク**（`src/lib/questions.ts`）で始める。
質問定義に「表示条件（業界・業態）」と「業界別の言い換え（variant）」を持たせるデータ駆動方式。

理由：MVPでは質問の品質・一貫性を優先する。ターゲット（マーケ未経験者）にとって
質問文言はサービスの核心なので、人間がコントロールできる状態を保つ。

### 再検討のトリガー

- 対応業界を大きく増やしたくなった場合
- 「その他」業界を選ぶユーザーが多く、汎用質問では体験が悪い場合

## LOG-007: 参考デザイン事例機能のDB・認証構成

**起票日**: 2026-07-12
**状態**: 方針決定

参考サイトの登録・Claude分析・保存・検索を導入するにあたり、Supabase接続と管理者認証の構成を検討した。

### 決定した方針

- **すべてNext.jsのAPI Route（サーバー側）経由**で実装する。Supabaseのsecret keyはサーバー専用モジュール（`server-only`）に隔離し、クライアント・ログ・レスポンスに露出させない
- **管理者認証はSupabase Auth（メール+パスワード）**を採用。`ADMIN_EMAILS`（環境変数）に載っているメールアドレスのみ管理者と認める
  - 自前のパスワード+Cookie方式も検討したが、暗号処理を自作せずに済み、将来の一般ユーザー認証（要件定義書の「認証は後付け」方針）にそのまま拡張できるSupabase Authを選択
- **検索APIは一般ユーザーも利用可**。RLSで「`status = 'published'` の行のみ誰でも読める・書き込みは不可」とし、書き込みはsecret key経由（管理者認証済みAPIのみ）に限定
- 管理者向け登録APIは「secret keyを使っている」ことに頼らず、**Cookieセッションを`getUser()`で検証してから**実行する

### 追記（2026-07-12 実装完了時）

- **スクリーンショット**は登録時にサーバー側のPlaywright（chromium）で取得し、Supabase Storageの
  公開バケット `screenshots` に `{id}.png` で保存。テーブルに列を増やさず `analysis.screenshotUrl`（jsonb内）に
  公開URLを持たせた（スキーマ変更のSQL再実行を避けるため。列に昇格させるのは今後の課題）
- 取得失敗時も**登録自体は成立**させる（スクショは任意扱い）
- 分析結果の編集は `PATCH /api/admin/references/[id]`（管理者のみ）。url と analysis 本体は編集不可、
  title / industry / style_tags / summary / status のみ許可リスト方式で更新
- E2E検証済み：ログイン → 登録（Claude分析+スクショ）→ 編集・保存 → RLS越しの公開API取得まで一連で動作確認。
  Vercel本番ではPlaywrightが動かないため、デプロイ時はスクショ取得の代替（外部API等）を要検討
- 注意：Playwright（約100MB）を依存に追加した。スクショ機能に必須のため

### 経緯メモ

- RESTルートへのpublishable keyアクセスが401「Secret API key required」を返したが、secret keyでは正常応答を確認。テーブル+RLS作成後にpublishable keyでの実読み取りを検証する（ルートエンドポイントの401だけでData API利用不可とは断定しない）

## LOG-008: 参考デザインのウィザード組み込み（デザインの好みステップ）

**起票日**: 2026-07-12
**状態**: 実装済み

### 決定した方針

- STEP 5 と STEP 6 の間に「デザインの好みを選ぶ」ページ（`/wizard/design`）を追加。
  **ステップ番号は変えず**、STEP 6 の一部として表示する（既存の localStorage・URL・進捗バーを壊さないため）
- 検索は「Claudeでユーザー回答を検索プロファイルへ正規化 → ルールベースのスコアリング →
  タグ重複ペナルティ付き greedy 選抜で3件（多様性確保）」の構成。
  スコアリングは `lib/designMatch.ts` に pure 関数として分離し、**将来 embedding / pgvector 検索へ
  差し替えるときはこのモジュールだけ交換**すればよい
- 候補名は参考サイト名を出さず、Claudeが初心者向けの方向性名（例：格調高い老舗の風格）を生成。
  失敗時はタグからルールベースで命名
- 選択後、Claudeが**デザイン設計書**（コンセプト・配色・タイポグラフィ・ファーストビュー・

  ルールを追加
- フォールバック：参考0件・検索失敗・設計書生成失敗・未選択のすべてで従来の標準デザイン生成を継続
- DB変更なし（既存 design_references と RLS をそのまま利用。新テーブルなし）

- E2E：候補3件表示（全カード画像付き）→ キーボード選択 → 設計書生成 → サイト生成で
  設計書の**カラーコード5件すべてが生成コードに反映**されることを確認
- 回答を変える（茶農家 vs ピアノ教室）と候補構成・順位が変わることを確認
- 既知の制約：Next.js形式で生成した場合のプレビューはコードがそのまま表示される（既存からの制約）

## LOG-009: 入力体験リニューアル（順番強制の撤廃・AIチャット中心のヒアリング）

**起票日**: 2026-07-14
**状態**: Phase 1〜3 実装済み（2026-07-14。フルSPA化のみ見送り）

### 背景（受け取ったフィードバック 2026-07-14）

- 入力項目が固定・判断しづらい内容だと入力側の負荷が上がる。音声入力・長文のAI処理・
  資料写真のアップロードなど「使い回せる情報」で簡単に多くの情報を引き出すべき
- 「あとで考える」ボタンは不要。未入力でもどんどん進め、後から埋められる導線にする。一時保存もほしい
- AIチャット相談は良い。「もう全部これで引き出せばよいのでは」
- チャットが回答状況を参照できていない → SPA的に1ページで遷移すればよい。
  チャットも tools / structured output を使えば任意形式のデータを取れる
- 順番じゃないとダメなUIは離脱する。入れられるところから入れて保存・再開できるのがよい

### 決定した方針（3フェーズ）

**Phase 1（今回実装）**
- `isStepClear` による「次へ」のロックを撤廃。必須の概念を「おすすめ」バッジに変更
- 「あとで考える（deferred）」ステータスを廃止。既存データは読み込み時に未入力へマイグレーション
- AIチャットを `wizard/layout.tsx` へ常駐化（App Routerのlayoutはステップ遷移で再マウントされない
  ため、**フルSPA化せずに**会話とチャット状態を維持できる。SPA化はPhase 3へ先送り）
- チャットへ全回答を注入：`/api/chat` に answers を渡し、既存の `buildPlanningContext()` で
  systemプロンプトへ展開
- 会話履歴を localStorage に保存し、離脱・再訪しても継続
- 「自動保存済み」の明示と、トップページの「続きから再開」導線

**Phase 2（今回実装）**
- チャットAPIに tool（質問ID + 回答値の配列）を定義し、AIが会話から引き出した内容を
  ユーザー確認付きでカードへ書き込む
- 「まとめて話す」一括入力：長文（スマホはOSの音声入力）を structured output で各カードへ振り分け。
  **音声入力の専用実装はしない**（OSのキーボード音声入力＋AI構造化で十分と判断）
- 回答状況一覧（未入力カードへジャンプ）と、生成前の「AIにおまかせする項目」確認

**Phase 3（2026-07-14 実装）**
- 資料写真（パンフ・チラシ・メニュー、最大3枚）→ Claude画像認識でカードへ振り分け。
  「まとめて話す」パネルに統合。写真はブラウザ側で長辺1568pxのJPEGへ縮小して送信
  （iPhoneのHEIC・APIの5MB上限対策）。**写真の保存はしない**（読み取りのみ。
  生成サイトに実素材を使う「素材アップロード」は別機能として今後）
- Supabase同期：`wizard_sessions` テーブル（**RLSポリシーなし = secret key経由のみ**。
  推測不可能なuuidの所持を本人確認代わりにするMVPの割り切り）。
  入力・チャットの変化を3秒デバウンスで自動同期し、「入力状況」パネルの
  引き継ぎリンク `/resume/{id}` で別端末から再開できる。
  **有効化には `supabase/migrations/20260714_wizard_sessions.sql` の手動実行が必要**
- AIインタビューモード：チャット初期画面の「🎙 AIインタビューで進める」から開始。
  systemプロンプトで「未回答の質問を1つずつ・回答は propose_card_updates で提案」を指示
- **フルSPA化は見送り**（下記）

### 検討した選択肢

- **フルSPA化を先にやる案** → 見送り。チャットの文脈維持が目的なら layout への持ち上げで足り、
  全面書き換えのリスクを取る必要がない。ステップページが薄くなった Phase 3 で自然に統合する
- **フルSPA化（Phase 3 時点の再判断・2026-07-14）** → 引き続き見送り。
  フィードバックのSPA提案の目的（チャットが回答状況・会話を維持する）は layout 常駐 +
  App Router のクライアント遷移で達成済みで、ルート統合はユーザーに見える改善がない。
  STEP 4〜6 にまだページ固有ロジックが残っており、統合はそれらが薄くなってから行う
- **音声入力の専用実装（Web Speech API / Whisper）** → 見送り。ターゲットはスマホユーザーで、
  OSのキーボード音声入力がそのまま使える。長文をAIで構造化する方が投資対効果が高い
- **チャット専用UIへの全面移行（「全部チャットで引き出す」）** → 段階移行。いきなりやると回答の
  確認・修正がしづらいため、「カード = 確認画面、チャット = 入力手段」の役割分担に寄せていく

### 検証メモ（2026-07-14 実装完了時）

- Playwright E2E で全17項目を確認：未入力のまま「次へ」で遷移／「あとで考える」の消滅／
  「おすすめ」バッジ／保存インジケータ／入力状況パネル／チャットが店名を記憶（回答コンテキスト注入）／
  チャットのカード記入提案 → 反映（tool use・実API）／ステップ遷移後の会話継続／
  トップの「つづきから再開」／STEP 6 生成前チェック／「まとめて話す」振り分け → 反映（実API）
- 発見・修正：ページ遷移時の lastPath 記録が「✓ 保存しました」を誤点灯させていたため、
  内部的な保存は通知なし（`saveWizardState(state, { notify: false })`）とした
- チャットAPIのレスポンスは NDJSON（`{type:'text'}` の差分 + `{type:'updates'}` の提案）。
  tool 入力の JSON は差分で扱いにくいため `finalMessage()` からまとめて取り出す実装
- 既存ユーザーの localStorage に残る `deferred` は読み込み時に `unanswered` へ自動移行（値は保持）

### 検証メモ（2026-07-14 Phase 3 実装完了時）

- Playwright E2E（実API）：テスト用チラシ画像から「喜多の園・茶・有機栽培」等を抽出して
  カードへ反映／インタビュー開始 → AIが質問 → 回答 → カード記入提案 → 終了、まで一連で確認
- 引き継ぎ（テーブル未作成の状態）：APIは503で案内文を返し、UIにも
  「同期機能がまだ有効になっていません」と表示されることを確認。
  存在しないIDの `/resume/{id}` はエラー画面 + トップへの導線を表示
- **残作業（ユーザー）**：Supabase ダッシュボード → SQL Editor で
  `supabase/migrations/20260714_wizard_sessions.sql` を実行すると同期・引き継ぎが有効になる
- 既知の課題：チャットのオーバーレイは外側タップで閉じない（✕ボタンのみ）。スマホでの
  使い勝手として次回改善候補

## LOG-010: 実素材アップロード（写真を生成サイトへ実掲載する方式）

**起票日**: 2026-07-23
**状態**: 決定済（実装済み）

### 背景

STEP 5 の「写真素材がある」チェックボックスは生成時に一切参照されない dead flag で、
「AIがサンプル画像を組み込みます」というUI上の約束も実際には果たされていなかった。
資料写真のAI読み取り（LOG-009 Phase 3）は情報の「抽出」のみで写真自体は使い捨てだったため、
実素材（商品写真等）を生成サイトに実際に載せる機能を追加した。

### 選択肢（写真の持ち方と生成サイトへの載せ方）

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| base64 を wizard_state に保存しプロンプトへ埋め込み | 外部依存なし | 同期上限2MB・localStorage割当を超える。再生成のたびに画像を送り直す |
| **Supabase Storage 公開URLをホットリンク（採用）** | STEP 7 の「HTML1ファイル手動デプロイ」が無変更で成立。再生成はテキストのみで安い | 生成サイトの画像が当サービスの Supabase に依存し続ける |
| zip 書き出しで画像を同梱 | 完全に自己完結したサイトになる | 多ファイル書き出し・デプロイ手順の作り直しが必要。MVP範囲を超える |

### 決定した方針

- 公開バケット `materials` に `{sessionId}/{uuid}.jpg` で保存（screenshots バケットと同じ
  auto-create パターン。SQLマイグレーション不要）。アップロード・削除は `/api/materials` 経由
  （secret key はサーバー専用の方針どおり）
- wizard_state には URL・種類・キャプションのみ保存（`step5.materials`）。`photosReady` は廃止（deprecated）
- アップロード時に AI が種類（商品/外観/店内/人物/ロゴ/その他）と短いキャプションを自動付与し、
  ユーザーが編集できる。生成は毎回テキスト（URL+キャプション）だけで済む
- 生成プロンプトに素材一覧と利用ルール（提供URLをそのまま使う・他の画像URLを作らない・
  種類ごとの配置ガイド）を追加。素材0件なら従来挙動を完全維持

## LOG-011: AI音声インタビューモード（OpenAI Realtime API + WebRTC）

**起票日**: 2026-08-10
**状態**: 決定済（実装済み）

### 背景

既存のAIインタビューはテキストチャット内のモード（LOG-009）で、音声は「まとめて話す」での
OS音声入力のみだった。ターゲット（スマホ利用の非IT経営者）にはタイピング自体が負担のため、
ChatGPT Voice のように「AIと話すだけで情報が集まる」体験を最優先で実装した。

### 選択肢（音声対話の実現方式）

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| Web Speech API + Claude + TTS | 追加コストほぼなし | ブラウザ差が大きく（特にiOS）、認識→生成→合成の直列処理で遅延が大きい。割り込み不可 |
| Whisper + Claude + TTS のターン制 | 制御しやすい | 3つのAPIの往復で応答まで数秒。会話の「間」が不自然 |
| **OpenAI Realtime API + WebRTC（採用）** | speech-to-speech一体型で低遅延。VADによる発話検出・割り込み（barge-in）が標準対応。iOS Safari含めWebRTCは全対象ブラウザで動く | AIプロバイダが2社になる。従量コストが比較的高い |

### 決定した方針

- **音声インタビューのみ OpenAI（`gpt-realtime`）を使い、Claude は既存用途（チャット・抽出・
  サイト生成）で継続**。音声UXの品質を既存構成への統一より優先（ユーザー指示）
- APIキー保護：`OPENAI_API_KEY` はサーバー専用。`/api/voice/session` が一時キー
  （client secret、10分）を発行し、ブラウザは一時キーだけで WebRTC 接続する
- インタビューの指示文・回答状況（`buildPlanningContext`）・tool定義はセッション作成時に
  サーバーで焼き込む。カードIDを enum で縛る方針は cardTool.ts と共通
- AIが `save_answers` ツールで抽出した回答は**確認なしで即カードへ保存**
  （テキストチャットの「反映する」確認は音声の会話を止めるため採用しない。
  保存はトーストで通知し、あとからカードで修正できることで担保）
- 状態機械：requesting_permission / connecting / listening / processing / speaking /
  muted / ended / error。semantic_vad により割り込みも最初から有効
- 音声が使えない環境（権限拒否・マイクなし・通信断）ではエラー画面から
  既存のテキストインタビューへフォールバックできる

### 記録するトレードオフ・既知の割り切り

- 会話の文字起こしは Realtime API の transcription（gpt-4o-mini-transcribe）に依存。
  表示用であり、カード保存の正とはしない（保存はAIの構造化出力ベース）
- インタビュー中の回答状況はセッション開始時のスナップショット。セッション中に手でカードを
  編集しても音声AIには伝わらない（インタビュー画面が全画面のため実害なし）
- 音声会話の履歴はテキストチャット履歴（wizard_chat）には残さない（MVPでは分離）
- コスト：gpt-realtime は音声入出力の従量課金。利用が増えたら `gpt-realtime-mini` への
  切り替えを検討（`lib/voiceInterview.ts` の `REALTIME_MODEL` 1箇所で変更可能）

### 検証メモ（2026-08-10 実装完了時）

- unit test（vitest）: tool定義のプロファイル出し分け・引数パースの境界値・指示文の組み立てを検証
- build / lint / tsc すべてパス
- **未検証（要実機）**: OpenAI との実接続（APIキー課金が発生するため）、
  iPhone Safari / Android Chrome での実機マイク・音声再生確認

## LOG-012: STEP 6 の Component-driven generation への移行

**起票日**: 2026-08-10
**状態**: 決定済（Phase 1〜4 実装済み）

### 背景

生成サイトの品質が実用レベルに達していなかった。原因分析の結果、モデルよりも
「AIに毎回ゼロからHTML/CSSを一括生成させる」構造が主要因と判断：

- system prompt が3行程度で、デザイン・レイアウトの判断がすべて毎回のAI出力任せ
- デザイン設計書は文章のままプロンプトに添えるだけで、機械的に強制されない
- 品質チェック・validation・部分修正がなく、修正=全再生成
- 16Kトークン上限にサイト全体のコードを詰め込むため、後半のセクションほど雑になる

### 決定

「ヒアリング → Site Brief + Design Tokens → Site/Page Data → Component Library → Renderer」
の Component-driven generation へ移行。AIの責務は
「preset/色/書体の選択」「コンポーネントとvariantの選択」「propsの文章生成」に限定する。

- **Design Tokens**（`types/site.ts` / `lib/site/tokens.ts`）: 5 preset（老舗・和飲食・
  食品生産・士業・サロン）+ AIによる色上書き。CSS Variables に変換して Renderer と
  静的書き出しで共有
- **Component Library**（`components/site/`）: 12カテゴリ・28コンポーネント。
  hooks不使用（クライアントプレビューとブラウザ側 renderToStaticMarkup の両対応）
- **単一情報源**（`lib/site/catalog.ts`）: props schema・AI向けJSON Schema・validation・
  Showcase 用サンプルpropsをすべて1つのカタログから派生。型の二重管理をしない
- **AI出力は必ず validation を通す**（`lib/site/schema.ts`）: 未知コンポーネント除去、
  壊れたprops の defaults 補完、素材IDの実在チェック、href のサニタイズ、
  ヘッダー・フッターの保証、stable ID 付与
- **placeholder**: 画像は material / url / placeholder を AssetReference で統一。
  写真ゼロでも崩れず、「入れるべき写真の内容」を提案として表示する
- **生成は2段階のAI呼び出し**（`lib/site/generate.ts`）: (1) brief+tokens、
  (2) 全ページのセクション構成（structured output・streaming）。
  モデルは環境変数 `CLAUDE_GENERATION_MODEL`（既定 claude-sonnet-5）/
  `CLAUDE_FAST_MODEL`（既定 claude-sonnet-4-6・既存機能は据え置き）で切り替え
- **静的HTML/Next.js の分岐は廃止**: 内部表現は React（SiteData）に統一し、
  公開時は `lib/site/exportHtml.ts` がブラウザ側で静的HTMLを書き出す
  （Tailwind Browser CDN + Google Fonts。従来の CDN 方針と同じ）
- **Showcase**（`/dev/components`）: 全コンポーネント×5 preset×3ビューポートと、
  3業種のサンプル構成（`lib/site/sampleSites.ts`）を確認できる

### 見送り・今後

- Puck（OSS版）導入・自然言語の部分修正（JSON Patch相当）・Agent SDK・
  スクリーンショットVisual QA は、Component-driven 生成の品質を確認してから
  次フェーズで実施（stable ID・canonical state はその前提で設計済み）
- 旧 `/api/generate`（一括コード生成）はロールバック用に残置。UIからは未使用

### 検証メモ（2026-08-10）

- vitest 102件（schema validation・catalog整合・サンプル構成の検証を含む）/ lint / tsc / build すべてパス
- Playwright でサンプル3業種 + 主要コンポーネントを 1440px / 390px でスクリーンショット確認。

## LOG-013: 表現の自由度の階層設計（テンプレ感の解消・Vibe Coding的自由度）

**起票日**: 2026-08-10
**状態**: 設計決定済。Layer 0/1（P5a）実装済み・Layer 2/3 は今後のフェーズ

### 背景

LOG-012 の Component-driven 化は品質・再現性を確保した一方、
「AIが固定28コンポーネントを選ぶだけでは生成サイトが似通う」という懸念（ユーザー指摘）。
分析の結果、似通いの主因はコンポーネント数ではなく
(1) セクション内部のスタイルが固定であること、(2) レイアウト構造を組み替える手段がないこと。

### 決定：自由度を4層に分け、AIは常に下の層から使う

| 層 | 内容 | 状態 |
|---|---|---|
| Layer 0 | Design Tokens に装飾の人格を追加（decor: headingAccent / imageTreatment / sectionDivider / motion） | **実装済み** |
| Layer 1 | Style Props：全セクション共通の `style`（background / spacing / align / containerWidth / headingScale / imageRatio / divider / motion）。全て token 範囲内の enum | **実装済み** |
| Layer 2 | Primitive 合成（ComposedSection）：Stack / Columns / Grid / Card / Heading / Text / Button / Image 等の制約付きレイアウトDSL。深さ・ノード数上限、absolute positioning は型レベルで不可 | P7 で実装 |
| Layer 3 | Custom React Component（escape hatch）：AI生成TSX + 品質ゲート（型チェック・静的解析 allowlist・レンダリングスモーク・Playwright Visual QA・失敗時は既存コンポーネントへフォールバック）。利用率5%未満の例外経路と位置づける | P8（Visual QA 基盤の上に）で実装 |

自然言語編集（P5b）は patch エンジンに集約：
patch_content / patch_style / set_tokens / replace_variant / reorder_sections /
compose_section / create_component から AI が1操作を選び、既存 validation を通して適用。
「高級感」等の形容詞→enum の対応表をプロンプトに明文化する。

### Layer 0/1（P5a）の実装方式

- `SiteSection.style`（types/site.ts）を追加。validation は `SECTION_STYLE_VALUES`
  （schema.ts）を単一情報源に、不正値は黙って捨てる（既定デザインに戻るだけ）
- **適用は Renderer のラッパー方式**：セクションごとに `[data-sid]` の div で包み、
  data 属性 + CSS 変数上書き（`sectionWrapperProps`）で反映。
  **28コンポーネント本体は無改修**（SITE_BASE_CSS の属性セレクタが反応する）
- `data-sbg="primary"` は CSS 変数の再割り当て（--s-text 等を onPrimary 系へ再マップ、
  凍結コピー --s-primary0 等を参照）で、どのコンポーネントを載せても可読性が壊れない
- decor はルート要素の data 属性（`rootDecorAttrs`）。preset ごとに既定の decor を持たせ、
  preset 選択だけでもサイトの個性が分かれる
- motion は CSS の `animation-timeline: view()`（非対応ブラウザでは無効・reduced-motion 尊重、JS不要）
- 生成プロンプトに「背景のリズム」「強弱は1〜2箇所」「中央揃えの連続を避ける」等の
  style 使用ルールを追加

### 既知の制限・今後

- headingAccent は SectionHeading を使うセクションにのみ効く（ヒーロー・Story系の
  見出しは対象外。意図的だが、必要なら s-heading フックの追加で拡張可能）
- pattern / wave 等の凝った sectionDivider・背景テクスチャは見送り（Layer 2 と合わせて再検討）
- Puck 導入時は Layer 1 の各キーがそのまま fields（select/radio）になる

### 検証メモ（2026-08-10）

- vitest 109件 / lint / tsc / build パス。Playwright で3サンプル（1440px/390px）を目視確認：
  rule/bar/underline アクセント・frame/offset の写真装飾・tint 背景・見出しの強弱・
  左揃え・セクション区切り線の反映を確認。data-sbg="primary" 上の CTA ボタン可読性も確認

- 必須スカラー欠落 → 「（あとで入力）」等の中立値（画像は中立 placeholder、CTAは「お問い合わせ」）
- 必須の items（リスト）が空 → 補完せず**セクションごと除外**（issue に記録）

特に hero バリエーション・kinetic typography・スクロール演出を decor / motion / Layer 2 の
ネタ元とする。

- UIは SiteEditPanel（提案チップ4種 + 自由入力）。初心者向けに内部操作は見せない

  FieldSpec→Puck fields（text/textarea/radio/select/object/array）、
  Layer 1 の SectionStyle は「見た目の調整」object field（おまかせ=空文字）として1:1対応。
  カテゴリは CATEGORY_LABELS でグルーピング。コンポーネント追加は catalog 1箇所の
  変更で AI 生成・validation・Showcase・エディタすべてに反映される
- **描画は SiteRenderer と同一経路**（prepareSectionProps + sectionWrapperProps +
  SITE_BASE_CSS + トークン CSS 変数）。iframe は無効化（enabled:false）し、
  アプリの Tailwind コンパイル済み CSS をそのまま使う
- **/editor ページ**：上部バー（ページタブ・「AIに修正を頼む」トグル・保存して戻る）+
  Puck 3ペイン + 右下に SiteEditPanel（P5b のAI編集）オーバーレイ。
  AI編集・Undo 適用時は Puck を key 再マウントで同期。編集は onChange で自動保存
  （notify なし。画面遷移時に通知付き保存）
- STEP 6 に「🎨 エディタで編集」導線

### 判明した Puck の挙動と対策

- **Puck は defaultProps を既存データの欠損 props にもマージする**。カタログの
  defaults（架空サンプル文）を渡すと LOG-014 で塞いだサンプル文混入が再発するため、
  エディタの defaultProps は中立初期値（neutralPuckProps）に差し替えた。
  ドラッグ追加時の初期文言は簡素になるが、保存データの汚染を防ぐことを優先
  （リッチな初期内容が欲しい場合は AI の add_section を使う）
